# Seven concepts became one — 2026-09-14

**The complaint:** "The agent framework still does not work properly and is overly complicated and
cumbersome with what happens where, what gates approve what… A personal family agent should be easy
to use, and this one, given that I created it myself, is riddled with issues."

**The evidence.** A TestFlight screenshot from a family member's phone: someone asked "can you call
me tomorrow two hours before to remind me", and the app answered with a card titled *Two-hour swim
lesson reminder*, labelled **2 steps · Manual · Low risk**, whose second step was
*"Alexa/Echo voice reminder unavailable"* — a step whose entire content is an apology. The app was
narrating its own machinery instead of doing the job.

## What was there

| Concept | What it was | Its own answer to "who approves this?" |
|---|---|---|
| Agent | identity + allow-list + deny-list | `approvalPolicy.unattended.includeHighRisk` |
| Skill | a deterministic step recipe | `approval_policy.gates` per step |
| Function | a user-authored wrapper over a tool, with a draft→available lifecycle and versions | `approval_required` |
| Playbook | a step list with no executor | — |
| Automation | client-local, not the same thing as a Trigger | — |
| Trigger | the real server-side schedule, in a different tab | — |
| Evolution | rewrote an agent's instructions after a failure | `autoApproveImprovements` |

Seven records, five gates, two of them in tabs the family had to keep in step by hand. Nobody —
including the person who built it — could say what would happen when a helper ran.

## What it is now

A **Helper** is a name, what it does written in plain English, when it runs, and one dial.

```
name          "Morning Briefing"
instructions  "Every morning, look at today's calendar and anything due today, and write
               the family one short, warm summary…"
schedule      manual | hourly | daily at HH:MM | weekly on a weekday at HH:MM
autonomy      ask  — Asks before it does anything
              act  — Does everyday things on its own, asks before sending or spending
              full — Does everything on its own, including sending and spending  (household PIN)
```

Running a helper **is** running Ask Famili with those standing instructions: the same tool loop, the
same tools, the same approval chain. The model reads real data, calls real tools, sees real results,
and writes back what it actually did. There is no plan to generate, no step list to render, and no
recipe that can drift from the tools it names.

Its own chat thread is its history. "What has this been doing?" is answered by reading it.

### The pieces

| | |
|---|---|
| `server/helpers.mjs` | create / update / delete / list, `runHelper()`, schedule sync |
| `server/helper-shape.mjs` | a dependency-free leaf: the schedule and autonomy vocabulary, who can see a helper, what it may reach |
| `server/context.mjs` | was `planner.mjs`, minus the brain: the live tool catalog and the household snapshot a turn is answered against |
| `server/orchestrator.mjs` | reduced to one job — starting the durable run an approval-gated tool becomes |
| `server/assistant-agent.mjs` | unchanged engine; `famili.propose_build` replaced by `list_helpers` / `create_helper` / `update_helper` / `run_helper` |

Helpers are stored in the same `agents` collection, so every helper a family already had keeps
working and nothing needed migrating. The fields that belonged to the removed concepts are simply no
longer read.

### What a family sees instead of a plan card

Asking for something recurring now creates the helper and says so. The assistant cannot propose a
build, because there is no build: `kind: "build"` is gone from both clients and every successful turn
is `kind: "answer"`.

## Deleted

`skills.mjs`, `functions.mjs`, `agents.mjs`, `agent-templates.mjs`, `automation-preflight.mjs`,
`evolution-revert.mjs`, the planner's `planFromGoal` / `assistantRespond` / `assistantStream` /
`proposeEvolution` / `judgeEvolutionConfidence` / `generatePlaybook`, the engine's evolution writer
and its registered-function executor, the assistant's self-repair loop, and 31 route handlers
(`/api/skills*`, `/api/functions*`, `/api/playbooks*`, `/api/evolution*`,
`/api/automations/validate`, `/api/agent-templates`, `/api/agent/plan`, `/api/assistant/build*`, and
the agent CRUD).

`GET /api/agents` survives as a read-only alias so a TestFlight build already on someone's phone
degrades to a list rather than an error screen.

### The self-repair loop, specifically

A failed run used to trigger a pass that asked a model to invent a *different* plan and ran it
unattended. It was the app's only "learning", and it learned nothing: the new plan came from the same
trace, from the same model that had just failed, with no observation of why. The tool loop retries
inside the turn, against real results, which is the only place a correction can be grounded.

## Seeding

`seedDefaults()` went from 763 lines to 150. A new household now gets its roster, its contact
methods, and one helper — the household assistant chat acts as. It does **not** get nine use-case
skills, two extra agents and sixteen playbooks written months before the tools they named.

Starter helpers are **offered**, not installed: `GET /api/helper-templates` returns editable
instructions a family reads and accepts, so what they end up with is something they agreed to rather
than something that appeared.

## Four permission bugs the new tests caught

The rewritten suites found these in the new code before it shipped. All four are in one
place, which is the argument for having one place:

- **Promotion.** `mayWriteHelper` read only the helper's *stored* visibility, so an Adult
  Member could edit the personal helper they legitimately own, pass
  `visibility: "household"`, and hand it to the whole family. The check now takes the
  requested visibility too.
- **Nest helpers.** A nest helper was editable only by whoever typed it first, so the other
  person in the nest could see and run it but not fix it — the opposite of what sharing it
  was for.
- **Revocation.** `deleteHelper` did not purge the helper from contact methods'
  `allowedAgentIds`. A helper's standing consent to message someone lives on the contact
  method, not on the helper, so deleting one left a live grant pointing at an id that no
  longer resolved.
- **Id squatting**, which made the one above exploitable rather than untidy. `createHelper`
  honoured a caller-supplied `body.id`, so an Adult Member could create a helper occupying a
  deleted helper's id and inherit the grant left behind. Closed from both sides: the grants
  are purged on delete, and the id is now server-assigned.

## A regression this caught

Approval-gated tools become durable runs *inside* the turn now, and a run posts its own result back
to the conversation from a background hook. Persisting the user's message after the model ran let
that result land above the question that caused it. Both assistant routes now write the user's turn
before calling the model, reading history first so the message being answered is not also handed back
as something already said. (`server/test/assistant-thread-order.test.mjs`)

## Still open

- Connectors still need setting up one at a time. The answer is an MCP client: `@ai-sdk/mcp` against
  the tool loop that already exists, so a household pastes one URL and that server's tools join the
  catalog with no bespoke connector module. Deliberately not bundled with this change.
- Sensitive Info Vault has no UI surface.
- Memory dedupe is exact-text only.
- `oauth.mjs rawFetch` and the Expo push calls still bypass `net.mjs`; no egress ledger.
- Playwright `tests/topgun` is still outside CI.
