# ADR-004: Rung 4 — native `famili.*` tools join the policy ladder; `plan_meal` becomes a declared composite

**Status:** Accepted · 2026-09-23 — owner decisions A, B and C taken (see the end): no native write requires approval, with the one exception C defines, which Stage 2 builds. Phase 2 (`plan_meal` as a declared composite, PR C) implemented 2026-09-23 on `rung4-plan-meal`, with owner decision B taken as recommended (grocery `source: "meal"`). PR B (Stage 1) implemented on branch `rung4-native-lane`; what it changed, including the few rows a family can see, is in the behaviour ledger.
**Scope:** Follow-up item 4 of [ADR-003](ADR-003-actions-not-agent-native.md) (the native tools), and the question ADR-003 left for this rung (`plan_meal`).
**Related:** ADR-003 · `server/assistant-agent.mjs` (`nativeTools`, `buildToolSet`) · `server/engine.mjs` (`executeToolForChat`) · `server/policy.mjs` · `server/internal-functions.mjs` (`homeops.plan_meal`) · `server/actions/meals.mjs`
**Evidence:** six read-only audits under [`docs/audits/rung-4/`](../audits/rung-4/README.md); every finding cited below carries a `file:line` there. Eleven findings were additionally challenged by adversarial verifiers and none was refuted; the remaining verification runs were cut off by a spend limit and the findings they would have covered are marked *(unverified)* where it matters.

## Context

### Phase 1 — what the native tools actually bypass

- **Sixteen `famili.*` tools** are defined by `nativeTools(ctx)`: six reads, six writes (`update_event`, `delete_event`, `update_task`, `delete_task`, `delete_meal`, `delete_memory`) and four helper-management tools (`list_helpers`, `create_helper`, `update_helper`, `run_helper`). The second loop of `buildToolSet` executes them as `await d.run(input)` plus one thin audit row. That path calls none of `resolveTool`, `isToolStepAllowed`, `resolveEffectivePolicy`, the `requiresApproval → queueApprovalRun` branch, `getRiskOverride` or `withTimeout`. The `add()` registrar records no `risk` and no `requiresApproval`, so there is nothing for a ladder to consult even if one were wired.
- **The ladder is live everywhere else.** The premise that `agent` is often `null` in chat is false: every production caller of `runAssistantAgent` passes an acting helper (`ensureDefaultHelper()` → `agt_household` for the app and 1:1 SMS, `resolveActingHelper` for the group lane, the helper record for helper runs). So the honest sentence is: *the ladder covers every catalog tool on every surface, and the native loop is the only tool-execution path outside it.* For app turns the acting helper ships with empty allow/deny lists and an empty `approvalPolicy`, so what actually bites today is rule 1 (kill switch), rule 4b (group only), rule 5 (risk override) and rule 7 (autonomy stance) — none of which a native write ever meets.
- **Concrete consequences, all verified:** rule 4b protects nothing native (a Limited Member in the group thread has catalog writes parked for an adult while `famili.update_task` / `update_event` / `delete_*` execute immediately); a household risk override recorded for a `famili.*` id can never take effect; helper allow/deny lists cannot address a `famili.*` id, so a family cannot deny a helper `famili.delete_event`; the kill switch is re-implemented by hand inside three native writes before their Google calls; native audit rows lack `connectorId`, `durationMs` and `agentId` and never emit `assistant.tool_blocked`; and the helper-management tools are still on the menu in the **group** channel for adults because `nativeTools` gates on `!ctx.asHelper` while only the prompt gates on `channel !== "group"` — a stated boundary enforced in prose only.
- **What a migrated tool cannot get for free.** `execResolved` hands an internal function exactly `{ householdId, actorId, runId, agentId }`; the native bodies read `session.role`, `ctx.channel` and the `session` object (`listHelpers(session)`, `publicHelper(h, session)`, `runHelper({ session })`). A declared action's `authorize` hook runs only at the HTTP door, never on the agent path. The run engine's `resolveToolBase` knows only `INTERNAL_FUNCTIONS`, providers and connectors, so **routing a native write through `queueApprovalRun` today ends as a failed run reading "Unknown tool: famili.update_helper"**, not a parked approval. `famili.run_helper` nests a full 240 s assistant turn; the catalog path's 60 s `withTimeout` would cut it off.
- **What approvals would look like on iOS** (the primary surface). The approvals pipeline is generic over `toolId`: Inbox titles the card with the raw dotted id and dumps the step input as `Label: value`; the Today `ApprovalSheet` shows `humanizeTool(toolId)` and the preview line but never the input, so an approver of a queued helper edit would never see the replacement instructions. Every parked/expired sentence assumes an outbound send ("nothing has been sent yet", "nothing was sent"), the approval TTL is 30 minutes, a missing `risk` defaults to **High** (Owner / Adult Admin approvers only), and the prompt promises helper edits are "created immediately" / "apply immediately". Two pre-existing iOS defects were found on the way: the Ask screen's live run card compares against `"waiting_approval"` while the engine writes `"waiting_for_approval"` (a parked run is badged "Doing it"), and `approval-sheet.tsx` maps the server's `approver_not_allowed` to the generic error alert.
- **Tests.** A ladder wrap that leaves `requiresApproval` unset changes **zero** existing assertions (no test asserts an `assistant.tool*` audit row, and the ladder's own tests pin that an ungated local Read/Write is untouched by every stance, the kill switch and rule 4b). Moving the tools into the catalog breaks `tool-registry-consistency.test.mjs` (it harvests native ids from the literal `add("famili.…")` text) and the role/channel assertions in `group-agent-turn`, `assistant-agent` and `assistant-delete-tools` unless role and channel are threaded through. Gating native writes under the default stance flips about nine assertions in two files, contradicts the prompt, and meets a ladder asymmetry: `isHighStakes` counts every Write, so an **"act"** helper's gated local write is refused by rule 6b ("sends or spends") before rule 7 can clear it. Playwright's web suites are not in CI and never drive a `famili.*` tool.

### Phase 2 — `plan_meal` against the rung 3 primitives

- `homeops.plan_meal` is a hand-written `INTERNAL_FUNCTIONS` entry doing seven things: title/slot/servings validation; ingredient normalisation (string or `{item, have}`, cap 60); self-enrichment of an ingredient-less meal through `web.mjs` (outbound page fetch and an OpenAI call); de-dupe by normalised title within 8 days (and against *any* date when no date is given); slot occupancy (`replace:true` archives the occupant, deletes its events and Google copies, unlinks its open groceries; otherwise shifts up to 7 days; otherwise double-books with a note); the meal via `newMealRecord`; groceries; one calendar event idempotent by `mealId`; a Google push when `calendarAutoSync` is on.
- **Three claims in the record are wrong.** ADR-003, the `meals.mjs` header and the `action-meals` test header all say `plan_meal` writes its groceries through `syncMealGroceries`. It does not: it has its own loop with a different title normaliser, `source: "assistant"` instead of `"meal"`, no visibility (a private meal's groceries land household-visible), a 60-item cap, and no in-loop de-dupe of same-named ingredients.
- **Two real gaps.** The Google push runs on `calendarAutoSync` alone with **no household kill-switch check** (the replace path's `deleteGoogleCopy` has one; `famili.update_event` has one; the policy ladder cannot see it because the capability is `delivers:false`). And `plan_meal` passes the model's `visibility` into `newMealRecord` unnormalised, never reads `nestId`, and writes its calendar event with no visibility at all, so a meal planned as private still produces a household-visible "Dinner: X" event.
- **Two more copies.** Meal→event composition (slot times, title, `startAt`, notes) is repeated in `PATCH /api/meals/:id` and `POST /api/meals/:id/to-calendar`; the retire cascade (events, Google copies, grocery unlink) is repeated in `DELETE /api/meals/:id` and `famili.delete_meal`, with small divergences in each.
- **It can be declared as it stands.** `http` is optional for an `agent:true` action (`create_list_item` is the precedent; a probe confirmed `defineAction` accepts it). The input fits the fence — `ingredients` as `items: { type: ["string","object"], properties… }` validates both branches and renders `Array<string | { item; have? }>`. The output fits with one hard limit: a nullable `$ref` is refused at load, so `event` must be an *optional* `$ref` (omitted when absent), not `EventRecord | null`. The result is consumed **flat** (`title`, `groceryItems`, `eventId`, `mealId`, `slot`, `google.pushed`, `note`) by the iOS run formatter (`apps/mobile/src/lib/format.ts`), `summarizeForCard`, the engine's `eventId` threading and nine assertions in four test files.
- **Composing the rung 3 primitives cannot reproduce it.** `createEvent` has no `mealId` input, writes `status: "draft"` and `provenance.via: "agent"` for an agent caller, and no declared update/replace primitive exists for the dupe, replace or existing-event branches; `create_list_item` composes via `.run`, which bypasses `invoke`, so inner calls gain no validation anyway.
- The id is load-bearing: `CHAT_DENIED_TOOL_IDS` is copied *by id* onto stored helper records, and `IDEMPOTENT_TOOLS` names it for restart replay. The `EXTRA_INPUT_KEYS` row for `plan_meal` is already fully redundant with its `INTERNAL_INPUTS` row.

## Decision

**Native tools: declare them, gate them with the same ladder, keep them where they are. Approvals for native writes are a product switch the household turns on later, not a side effect of this rung.**

Every `famili.*` tool becomes a `defineAction` (id unchanged, `agent: true`, no `http`), which gives it a `risk`, `requiresApproval: false`, `delivers: false`, a declared input and output, generated types, and a place in the registry that `tool-registry-consistency` can read instead of scraping source text. They are **not** spread into the catalog or `INTERNAL_INPUTS` in this rung: the model still receives them from `nativeTools` through the same second loop, and that loop now calls one shared gate, extracted from `executeToolForChat`, that runs `isToolStepAllowed` → `resolveEffectivePolicy` (with `actorIsAdult` in the group channel) → per-action `withTimeout` → the engine's audit rows (`assistant.tool` with `connectorId` / `durationMs` / `agentId`, `assistant.tool_blocked` on refusal). Because every native `requiresApproval` is declared `false`, the household's stance never changes a native verdict, and what the ladder can do to a native tool in Stage 1 is narrower than "the ladder": a helper's allow/deny lists (rules 2/3) reach native tools for the first time, and a native tool listed in a helper's `alwaysApprove` (rule 4), or a native write listed in its `autoAllow` (rule 6, which refuses to relax any Write), is **refused in words** rather than silently run, because Stage 1 cannot park it. Rule 1 cannot fire — native writes are local, and their Google calls ask `googleReachAllowed` inside `run` — and rules 4b and 5 act only on a tool that requires approval by default, so they do nothing for native tools until Stage 2. The intended behaviour change is the closing of a stated boundary: the helper-management tools leave the group-channel menu. The rest of what shipped, including the few rows a family can see, is in the behaviour ledger.

*Why not the catalog path now?* The audits price it: role and channel threaded through `execResolved` for every internal tool and the run path (which stores no role), a catalog exposure predicate the catalog cannot express today (role, channel, `asHelper`), helpers with a non-empty allow-list silently losing every native read, two declared reads over the same data, and a rewrite of the prompt names. All of that buys exactly one thing the shared gate does not: run-engine reachability, which only matters once a native write can require approval. That is Stage 2, and it is gated by the owner decisions below, because it is the point where the iOS Inbox, the prompt's "applies immediately" promise and the 30-minute TTL become visible.

**`plan_meal`: a declared composite in `create_list_item`'s sense — one action, one run body, shared helpers underneath — not a composition of `createMeal.run`.**

`homeops.plan_meal` moves into `server/actions/meals.mjs` as a `defineAction` with the same id (agent-only), a declared input (`ingredients` as the string-or-object union, `visibility` and `nestId` resolved through `resolveVisibility` exactly as `createMeal` does, a real `description`), and a declared output that **keeps every flat key** and adds `meal: MealRecord` plus an optional `event: EventRecord`. Its body keeps the dedupe/replace/shift/enrichment semantics verbatim — those are product features with tests — but its three side effects go through shared helpers so there is one writer of each: `syncMealGroceries` (extended to return ids and to take the punctuation-insensitive normaliser), a new `mealEventFields(meal, timeZone)` lifted from the three copies of slot-time/title/notes composition, and a new `retireMeal(meal, ctx)` lifted from the three copies of the archive-and-clean-up cascade. The Google push gains the missing `externalActionsEnabled !== false` guard in-run, and the event inherits the meal's visibility. The action stays `delivers: false`: declaring it `delivers: true` would make the kill switch refuse the local meal and groceries too and make rule 6 unable to clear it.

### Consequences

**Good.** One gate for every tool the model can call; helper allow/deny lists reach native tools, and "always ask me" / `autoAllow` on a native tool refuse it instead of being ignored (risk overrides and rule 4b reach native tools only in Stage 2, when a native tool can require approval; the kill switch never needs to, since native writes are local and check `googleReachAllowed` before any Google call); one audit shape; a per-action timeout that fits `run_helper`; the group-channel helper boundary enforced in code and pinned by a test; `tool-registry-consistency` reads the registry instead of regexes; generated `FamiliUpdateEventInput` … `FamiliRunHelperResult` types on both clients (namespaced because `famili.list_events` / `list_tasks` / `list_meals` would otherwise export the same `ListEventsInput` … names as `homeops.list_*` and fail to compile); `plan_meal` validated on both paths for the first time, with one grocery writer, one meal→event composer and one retire cascade instead of three or four; the kill-switch and visibility gaps closed; `EXTRA_INPUT_KEYS` loses its `plan_meal` row and the ADR-003 record is corrected.

**Bad.** Native tools remain a second *dispatch* loop until Stage 2 — the gate is shared, the wiring is not. Two declared reads over the same data (`homeops.list_events` for HTTP, `famili.list_events` for the model) persist by design. `bad_slot` becomes `invalid_input` with `field: "slot"`, as `create_task` already did; `bad_servings` is kept, because `servings` keeps `createMeal`'s wide wire and `run` still refuses zero and words out loud; one assertion changes. Grocery items written by `plan_meal` change `source` (see owner decision B).

**Accepted risk.** A helper with a *non-empty* `allowedToolIds` used to get every native tool regardless; after Stage 1 it is refused any native tool that is not on its list (`not_permitted_not_permitted`), because a non-empty allow-list means "only these". One seeded helper has such a list: **"Famili in chat" (`agt_chat`)**, seeded with `allowedToolIds: ["sms.send"]` the first time a household's group thread is seen (`server/group-chat.mjs` `ensureChatHelper`), listed in Helpers, and runnable by an Owner or Adult Admin with Run now. A manual run of it is now refused every native read and write — correctly: it is the group listener's identity, the list is the one tool it may use, and its own Lane 1 work goes through `executeToolForChat` against that same list. The Helpers UI cannot yet put a `famili.*` id on a list, so no family can widen it until Stage 2. Both halves are pinned in `native-actions.test.mjs` (the allow-list refusal as a unit, and a real Run now of the seeded `agt_chat`), so this is deliberate, not silent.

Playwright's web suites are run as a proxy (they are not in CI and do not drive native tools); iOS is verified by `tsc` + `expo export` until a simulator is available, and every iOS-facing change is called out as visually unverified.

### PR B — Stage 1: the declared native lane (no visible change except the group-channel helper menu)
1. **Schemas.** `server/actions/native/*.mjs` — one `defineAction` per `famili.*` tool, ids unchanged, `agent: true`, no `http`, `risk` explicit (`Low` for reads and self-edits, `Medium` for deletes and helper writes), `requiresApproval: false`, `delivers: false`, `input` = today's `schema` (already fence-compatible), `output` declared from today's result shapes, a `timeoutMs` field (`run_helper`: 300 000; others: 60 000) and an `available(ctx)` predicate (`managesHelpers` = role ≥ Adult Member ∧ `!asHelper` ∧ `channel !== "group"`; reads and writes always — a write stays on a read-only profile's menu and refuses inside `run` with `read_only_profile`, as it always did). `define-action.mjs` learns `lane`, `timeoutMs` and `available` as optional, validated fields. The bodies move unchanged from `nativeTools` into each action's `run(ctx, input)` with the ctx contract **`{ householdId, actorId, role, channel, session, via: "agent", runId: null, agentId, asHelper }`** — `session` is passed because `listHelpers` / `publicHelper` / `runHelper` take it; this is the native lane's contract, not `execResolved`'s.
2. **Registry.** `server/actions/registry.mjs`: `NATIVE_ACTIONS` list, included in `ACTIONS` (so `getAction`, generated types and the duplicate-id check cover them) but excluded from `AGENT_ACTIONS` / `ACTION_INTERNAL_FUNCTIONS` / `ACTION_INPUTS` via a `lane: "native"` marker. `npm run generate:actions` and commit both copies.
3. **The gate.** `server/engine.mjs`: extract the body of `executeToolForChat` between `resolveTool` and `execResolved` into `export function gateToolCall({ cap, toolId, agent, householdId, actorId, conversationId, actorIsAdult, requiresApproval })` returning `{ blocked, needsApproval, decision, error, message }` (`requiresApproval` is the pre-ladder gate the no-agent branch decides on; `decision` is null there); `executeToolForChat` calls it unchanged (its tests pin the behaviour). Add `export async function runNativeAction({ action, input, session, agent, channel, conversationId, asHelper, actorIsAdult })` that builds the cap from the action, calls `gateToolCall`, refuses with the same `policy_<rule>` / `not_permitted_<reason>` errors and `assistant.tool_blocked` audit, refuses a `needsApproval` verdict (rules 4 and 6) in one sentence of its own, wraps `action.invoke(ctx, input)` in `withTimeout(action.timeoutMs)`, and writes the engine's `assistant.tool` row.
4. **Dispatch.** `server/assistant-agent.mjs`: `nativeTools(ctx)` becomes `NATIVE_ACTIONS.filter(a => a.available(ctx))`; the second loop of `buildToolSet` calls `runNativeAction` and records `blocked` (new for natives) alongside `done` / `failed`. Delete the inline kill-switch reads — two in `update_event` and one in `delete_event` when PR B started; PR C had already moved `delete_meal`'s into `retireMeal` — in favour of one `googleReachAllowed(householdId)` helper in `server/calendar.mjs` used by the native writes and by `plan_meal` (PR C). `ctx.helperChanged` is deleted (no consumer on either client). The prompt keeps `famili__*` names.
5. **Tests.** `tool-registry-consistency.test.mjs`: native ids come from `NATIVE_ACTIONS`, not the source regex. New `native-actions.test.mjs`: every native action loads and is frozen; `agt_household` with `deniedToolIds: ["famili.delete_event"]` → status `blocked`, `assistant.tool_blocked` row, nothing deleted; "always ask me" and a write's `autoAllow` refuse a native tool in words (there is no risk-override test: rule 5 has nothing to clear on a tool that never requires approval, so it is a no-op until Stage 2); kill switch refuses a Google-reaching native write with the canonical sentence; group-channel menu excludes the four helper tools (`group-agent-turn` gains the assertion); `run_helper` is not cut at 60 s; audit rows carry `durationMs` and `agentId`. Existing assertions in `assistant-agent`, `assistant-delete-tools`, `helpers`, `group-agent-turn` stay as they are.

### PR C — `plan_meal` as a declared composite (no visible change except the rows marked)
1. `server/actions/meals.mjs`: `syncMealGroceries(meal, session, { norm })` returns `{ added, ids }` and takes the punctuation-collapsing normaliser as the default; new exported `mealEventFields(meal, timeZone)` and `retireMeal(meal, ctx)`; `planMeal = defineAction({ id: "homeops.plan_meal", … })` with the input/output above, `errorCodes: ["invalid_input", "empty_title", "bad_servings", "not_in_nest"]` with `errors: { not_in_nest: 403 }` (the one code with an HTTP status, exactly as `createMeal` maps it), body moved from `internal-functions.mjs` with the Google push guarded by `googleReachAllowed`, groceries via `syncMealGroceries`, the event via `putEvent(newEventRecord({ ...mealEventFields(meal, tz), visibility: meal.visibility, nestId, mealId, provenance: { via: "meal", … } }, ctx))` or `patchEvent(existing.id, mealEventFields(...))`.

### Stage 2 — the group-thread park for non-adults (decision C), and nothing broader (decision A)
Scope, as decided: exactly one native approval exists — a non-adult's native **write** in the group thread (decision C). No stance, autonomy tier or per-tool setting makes any other native write ask (decision A), so the helper trio, and every native write in the app, 1:1 SMS and helper runs, stay immediate and the prompt's "created immediately" / "applies immediately" stays true there. Stage 2 also closes the channel-visibility gaps listed under C. What the one approval needs: `resolveToolBase` resolves `NATIVE_ACTIONS`; `execResolved` threads `role` and `channel` (the run must store the actor's role at start); `queueApprovalRun` passes the evaluating `agentId` and `actorIsAdult` so the run reproduces the chat verdict (a pre-existing gap: today a step parked under rule 4b is re-evaluated without it and can execute under a Trusted stance). Every one of those is visible on iOS.

## Decisions for the owner

All three decided by the owner on 2026-09-23:

- **A — No.** No native write requires approval, under any stance, autonomy tier or per-tool setting. The single exception is C.
- **B — Yes.** `plan_meal`'s grocery items are `source: "meal"` (shipped in PR C).
- **C — Yes, in Stage 2.** A non-adult's native write in the group thread is parked for an adult; Stage 2 builds it and closes the channel-visibility gaps listed under C.

The questions as they were put:

**A. Should any native write ever require approval, and which?** Recommendation: not the helper trio (already role-gated, never in the group, and the prompt promises immediacy); consider `delete_event` / `delete_meal` / `delete_memory` under the **Cautious** stance only, and only after Stage 2 fixes the rule 6b asymmetry and the Inbox/TTL/copy issues, so the family sees "Waiting for approval · Delete an event" with the input shown. Nothing in PR A–C depends on this answer.

**B. Grocery items written by `plan_meal`: `source: "meal"` (one writer, the user door's value) or keep `"assistant"`?** Recommendation: `"meal"` — the `mealId` link is the provenance that matters and the record then has one writer; `task-record-contract.test.mjs` is adjusted to seed its `"assistant"` fixture directly. If the iOS groceries screen ever surfaces `source`, this is the one line a family could notice.

**C. Should a non-adult's native WRITE in the group thread be parked for an adult, as rule 4b parks catalog writes?** Recommendation: yes, in Stage 2 — by declaring a native write's `requiresApproval` true only when `channel === "group"` and the actor is not an adult, so it rides the approval pipeline once `resolveToolBase` can reach native tools. Until then a Limited Member in the group thread can still complete, re-date or reassign their own tasks, move their own events and delete their own tasks, events, meals and memories **immediately**, with no approval record: rule 4b parks only what a capability itself gates, and no native tool is gated. `native-actions.test.mjs` pins this as the Stage 1 behaviour (a Limited Member's `famili.delete_task` in the group lane runs at once), so changing it is this decision, not a side effect. Two pre-existing gaps belong with it: `famili.delete_event` has no channel visibility check (unlike `update_event`, which asks `seeable`), and `famili.delete_memory` ignores the channel (`canForgetMemory` looks only at the person) — so in the group thread, given an id, either can delete a private item and echo its title or text into a thread people outside the household read. `delete_task` and `delete_meal` have no `seeable` check either.
