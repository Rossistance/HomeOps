# Rung 4 audit — executeToolForChat and the policy ladder as a contract (2026-09-23)

SUMMARY: executeToolForChat (server/engine.mjs:384-434) is the single agent-side execution seam: resolveTool → isToolStepAllowed → resolveEffectivePolicy → execResolved, and it only runs the ladder when an `agent` is supplied; the run loop (_drive, engine.mjs:722-894) repeats the same chain per step but without `actorIsAdult`. execResolved hands an internal function exactly `{ householdId, actorId, runId, agentId }` (engine.mjs:319); nothing about the session (role), the channel, onToolStart or helperChanged crosses that boundary, and the only other production caller of a declared action's `invoke` is the HTTP door (server/actions/routes.mjs:31), which does pass `role` and `via:"user"`. define-action.mjs mentions executeToolForChat only in its header comment; toInternalFunction contributes id/name/description/action/risk/requiresApproval/delivers/connectorId/connectorName plus `run(ctx,input) → invoke({ via:"agent", ...ctx })`, and the action's `authorize` hook is never called on the agent path. The kill switch (rule 1) and execResolved's defence both use reachesOutside(), which for an internal tool is `delivers===true || action in Send/Download/Pay`; `homeops.plan_meal` is Write/Low/delivers:false yet pushes to Google Calendar when calendarAutoSync is on, with no externalActionsEnabled check on that push. Policy rule 4b (actor.not_adult) is only ever asserted in the chat turn on the group channel; the durable run that a needsApproval verdict becomes re-runs the ladder without it, so under a Trusted stance a Limited Member's parked step can execute with no human approval. A declared action reaches the model via ACTION_INTERNAL_FUNCTIONS → INTERNAL_FUNCTIONS → toolCatalog row (context.mjs:153, with description) → pruneCatalogForPrompt (agent allow/deny only, every homeops.* row kept unconditionally, no session-role filter) → buildToolSet (assistant-agent.mjs:683-725) which uses getAction(id).input verbatim as the AI SDK schema. The run-loop input fill comma-joins arrays and validateInput's coerce only handles boolean/number, so a declared array-typed input filled by the engine would fail invalid_input. A migrated native tool would inherit a 60s withTimeout, the `{ok,result}|{ok:false,error,message,waiting?,needsSetup?}` result contract, the at-most-once quarantine on restart unless listed in IDEMPOTENT_TOOLS, and would lose access to session.role/channel unless the ctx object at engine.mjs:319 and both its callers are extended.

## FINDINGS

### F1 [high]
execResolved passes an internal function exactly `{ householdId, actorId, runId, agentId }` and nothing else; session.role, channel, the session object, onToolStart and helperChanged never cross executeToolForChat, whose signature has no `channel` parameter at all. The chat caller sets runId:null/accountId:null (accountId is dropped for internal tools anyway); the run caller sources everything from the run record, which stores no role.
IMPLICATION: Every native famili.* tool reads `session.role` (canWrite), `ctx.channel` (seeable) and mutates `ctx.helperChanged`; none of that is reachable from a declared action's run today. Adding role/channel is a ONE-site change in execResolved (line 319) plus two caller threads: executeToolForChat already holds `session` (role) but needs a new `channel` param (today channel is collapsed into actorIsAdult at assistant-agent.mjs:703); _drive has only run.actorId and run.sourceRef.via, so a run would need role looked up or stored on the run. The HTTP door (routes.mjs:31) already passes role. No other production site constructs an internal-function ctx: helpers.mjs, group-agent.mjs, sms.mjs and index.mjs all go through runAssistantAgent → buildToolSet → executeToolForChat; actions/tasks.mjs:144 (`createTask.run(ctx, ...)`) is a pass-through.
EVIDENCE: server/engine.mjs:319; server/engine.mjs:426; server/engine.mjs:894; server/engine.mjs:384; server/assistant-agent.mjs:911-919; server/actions/routes.mjs:31; server/actions/define-action.mjs:202

### F2 [high]
A declared action's `authorize` hook runs only at the HTTP door; the agent path (execResolved → def.run → invoke) never calls it and carries no role to call it with. The role floor that createTask/createMeal declare (`roleAtLeast(session?.role, "Limited Member")`) therefore applies to POST /api/tasks but not to homeops.create_task called from chat.
IMPLICATION: Migrating a native tool's `canWrite`/`readOnly()` refusal into a declared `authorize` would silently drop it for chat callers. A migrated action needs either (a) execResolved/executeToolForChat to call `authorize(session)` before `run`, or (b) the role carried in ctx and checked inside `run`. define-action.mjs's only reference to executeToolForChat is the header comment quoted above; nothing in the file is wired to the ladder.
EVIDENCE: server/actions/routes.mjs:22; server/actions/define-action.mjs:173-180; server/actions/tasks.mjs:63; server/assistant-agent.mjs:271-272; server/actions/define-action.mjs:16-17

### F3 [high]
Policy rule 4b (actor.not_adult) is asserted only by the catalog-tool path in buildToolSet on the group channel. The run loop's resolveEffectivePolicy call passes no actorIsAdult, and queueApprovalRun/orchestrate accept none, so a step that executeToolForChat parked under 4b is re-evaluated in _drive without it; under settings.autonomy="Trusted" (rule 7) that step resolves ALLOWED and executes with no approval, and queueApprovalRun reports it as `completed`. The group proposal path (resolveProposal) never passes actorIsAdult either. Separately, the queued run resolves its helper via orchestrate → resolveActingHelper (agentId is not forwarded), so the run's ladder can run against a different agent than the one executeToolForChat evaluated.
IMPLICATION: The needsApproval → run handoff is not verdict-preserving: the run re-derives the verdict from a smaller input set (no actorIsAdult, possibly a different agent). A migrated native tool that relies on 4b for child-safety in the group lane would be bypassed the moment its step is queued. If rung 4 keeps the two-ladder shape, the run must carry the chat verdict's inputs (actorIsAdult, agentId) on the step or sourceRef, or startRun must honour a caller-supplied `requiresApproval:true` (today startRun:521 overwrites it with resolveTool's value).
EVIDENCE: server/policy.mjs:144-146; server/assistant-agent.mjs:703; server/assistant-agent.mjs:710-712; server/engine.mjs:765-782; server/policy.mjs:250-254; server/group-chat.mjs:1193-1196; server/orchestrator.mjs:116-117; server/test/group-attribution.test.mjs:266-273

### F4 [high]
For an internal tool, 'reaches outside' means `delivers===true` or action Send/Download/Pay; `external` is derived from resolved.kind and is always false for kind:"internal". homeops.plan_meal is Write/Low/requiresApproval:false/delivers:false, so neither policy rule 1 nor execResolved's defence applies, yet its step 4 calls pushEventToGoogle whenever settings.calendarAutoSync is true, and neither plan_meal nor pushEventToGoogle checks externalActionsEnabled on the push (only the deleteGoogleCopy branch does). The native famili.update_event tool does check the kill switch before the same push.
IMPLICATION: An internal tool that composes an outbound side effect is invisible to the kill switch and to rule 7's Balanced bound unless it declares `delivers:true` or an action of Send. The same Google write via the provider tool calendar.create is Medium/approval-gated/external. defineAction only allows action Read|Write|Send and has no `external` field, so a declared composite (plan_meal, or a migrated famili.update_event that pushes to Google) can only be made to reach outside via `delivers:true` (which also makes it high-stakes for rules 6/6b) or by checking externalActionsEnabled inside `run` as the native tool does today.
EVIDENCE: server/policy.mjs:56-60; server/engine.mjs:312-314; server/engine.mjs:405-406; server/internal-functions.mjs:290-293; server/internal-functions.mjs:440-444; server/internal-functions.mjs:361-362; server/calendar.mjs:493,508-509; server/assistant-agent.mjs:424-425; server/providers.mjs:177

### F5 [medium]
executeToolForChat runs isToolStepAllowed and resolveEffectivePolicy only inside `if (agent)`; with agent null it falls straight to the tool's override-adjusted requiresApproval and executes. All current production callers pass an agent, but the export defaults `agent = null` and there is no channel parameter, so a migrated native tool's safety depends on every future call site remembering to attribute.
IMPLICATION: isToolStepAllowed ignores its third argument (engine passes `{ householdId, actorId }` to a two-parameter function). A contract for migrated tools should make `agent` required on executeToolForChat, or fail closed when absent, rather than treating null as 'no policy'.
EVIDENCE: server/engine.mjs:391-392; server/engine.mjs:420; server/sms.mjs:331-334; server/helper-shape.mjs:95-96

### F6 [medium]
A declared action reaches the model as a toolCatalog row `{ toolId, name, action, risk, requiresApproval, connectorId, connectorName, source:"internal", connected:true, inputs, description }` (risk/requiresApproval rewritten by the household/nest risk override for the session actor). pruneCatalogForPrompt filters only by the agent's allow/deny lists and keeps every `source:"internal"`/`homeops.*` row unconditionally — including ones on the agent's deny list — and never consults session.role. buildToolSet then builds the AI SDK tool from the FULL row (not the pruned projection): the description string embeds action/risk/description plus an approval note derived from the override-effective `requiresApproval`, and the input schema is `getAction(id).input` verbatim.
IMPLICATION: Once a famili.* tool becomes a declared action it lands on every helper's menu regardless of deny-list (blocked only at execution with `not_permitted_denied`), and the approval note the model reads reflects the risk override, not the ladder verdict (agent alwaysApprove/autoAllow/unattended/stance are not visible in the description). Role-based menu shaping (today done inside nativeTools via canWrite and the group-only managesHelpers flag) has no equivalent in the catalog path.
EVIDENCE: server/context.mjs:153; server/context.mjs:205-207; server/context.mjs:243-245; server/assistant-agent.mjs:672; server/assistant-agent.mjs:690-693; server/assistant-agent.mjs:132-134; server/internal-functions.mjs:612

### F7 [medium]
The run-loop input fill turns every array value into a comma-joined string, and defineAction's validateInput (coerce:true) only coerces boolean and number from strings, so a declared action with an array-typed input reached via a run step whose input needed filling receives a string and fails with invalid_input.
IMPLICATION: The chat path is unaffected (the model emits JSON matching the declared schema and inputNeedsFill never runs there), but the run path (scheduled helpers, queued approvals, manual plans) sees only INTERNAL_INPUTS key rows, not the declared JSON Schema, so a migrated tool with array inputs (participantIds, remindOffsets, ingredients) is only safe in a run when its input arrives complete. Rung 4 should either teach fillStepInput the declared schema or have execResolved split comma strings for array-typed properties.
EVIDENCE: server/engine.mjs:253-258; server/actions/define-action.mjs:82-87; server/actions/define-action.mjs:95-96; server/engine.mjs:172-178

### F8 [low]
resolveTool's three shapes: internal → `{ kind:"internal", def, requiresApproval, action, risk, connectorId, connectorName }`; provider → `{ kind:"provider", provider, tool, requiresApproval, action, risk, connectorId: provider.id, connectorName }`; connector → `{ kind:"connector", connector, tool, ... }`. `baseRequiresApproval` and `riskOverridden` exist only when a risk override is present (hence `resolved.baseRequiresApproval ?? resolved.requiresApproval` at both ladder sites); the `kind === "function"` branch startRun checks is never produced. The execution contract a migrated tool inherits: 60s withTimeout (native tools today have none; the AI SDK step timeout is 120s), a `{ok,result}|{ok:false,error,message,waiting?,needsSetup?}` result, 200-char result summaries in the run trace, and at-most-once quarantine on restart unless the id is in IDEMPOTENT_TOOLS.
IMPLICATION: A declared action is exactly what resolveToolBase's `internal` branch reads (id, action, risk, requiresApproval, delivers, connectorId/Name, run); it contributes no `external`, `draft` or `authorize` to the engine. Because `...(ctx ?? {})` spreads after `via:"agent"`, any future ctx field named `via` from the engine would override it. Migrated tools that are not idempotent-by-construction will be quarantined (failed) if a deploy lands mid-step unless added to IDEMPOTENT_TOOLS.
EVIDENCE: server/engine.mjs:263-275; server/engine.mjs:290-297; server/engine.mjs:397; server/engine.mjs:517; server/engine.mjs:30,87-89; server/assistant-agent.mjs:738; server/engine.mjs:1252; server/actions/define-action.mjs:196-203
