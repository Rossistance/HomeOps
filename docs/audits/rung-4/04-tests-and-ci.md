# Rung 4 audit — tests that pin the behaviour, and CI (2026-09-23)

SUMMARY: I read the shared harness (server/test/harness.mjs spawns the REAL server per file on an ephemeral port with an isolated HOMEOPS_DATA_DIR; makeSession POSTs /api/session as a seeded member; fake-model.mjs scripts an OpenAI-compatible LM Studio endpoint and records every request) and the 16 test files in scope, then traced what they pin against server/assistant-agent.mjs, server/engine.mjs and server/policy.mjs. Native famili.* tools are pinned by exactly six server test files (assistant-agent, assistant-delete-tools, helpers, group-agent-turn, tool-registry-consistency, action-reads; group-injection uses "famili.list_events" only as a pure cap id); the ladder's rule strings are pinned by policy-resolution, autonomy-presets, unattended-override, runs-unattended-honesty, group-authorization and group-injection. One premise in the brief is wrong per code: `agent` is never null on any chat path — index.mjs passes ensureDefaultHelper() (agt_household), sms.mjs and group-agent.mjs pass resolveActingHelper(), helpers.mjs passes the helper record — so shape (a) would run the `if (agent)` ladder branch on every native call. Because agt_household seeds empty allow/deny lists and `approvalPolicy: {}`, and every native is a local Read/Write with requiresApproval unset, (a) changes zero existing assertions (natives already emit an `assistant.tool` audit row; no test asserts `assistant.tool*` rows). Shape (b) touches five files for certain: tool-registry-consistency derives native ids from the literal `add("famili.…")` text and resolves famili__ names only against that set; the native closures depend on `session.role` and `ctx.channel`, which execResolved's ctx `{ householdId, actorId, runId, agentId }` does not carry (breaking the channel-gate assertion in group-agent-turn, the read_only_profile assertion in assistant-agent, ownership assertions in assistant-delete-tools); and helpers.test pins that a helper run's tool menu omits famili__create_helper, which is a nativeTools-time role/asHelper filter, not an agent permission. Shape (c) breaks about nine assertions across assistant-agent and assistant-delete-tools (update_event ["done","done"], create_helper before+1, four delete "done"s) because an unset stance resolves to capability.requires_approval, and it exposes a ladder trap: policy.mjs isHighStakes counts every Write, so an "act" helper's gated local write hits rule 6b's agent.unattended_refused ("sends or spends") before rule 7 can clear it; (c) also needs (b) first because queueApprovalRun parks a run whose toolId the run engine's resolveToolBase cannot resolve. Playwright specs in tests/topgun/web are not in .github/workflows/ci.yml (only PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD appears; CI runs npm test, typecheck, build, mobile tsc + expo export), and helper-agents-nav asserts nav entries ("Skills", "Functions", "Automations") that server tests describe as removed.

## FINDINGS

### F1 [high]
The brief's premise that `agent` is typically null in personal chat is false: every runAssistantAgent call site passes an acting helper (agt_household for app chat and 1:1 SMS, the helper record for helper runs, resolveActingHelper for the group lane), so under shape (a) the `if (agent)` ladder branch in executeToolForChat would run on every native call.
IMPLICATION: Shape (a) must be designed for agent always present. agt_household seeds `allowedToolIds: [], deniedToolIds: [], approvalPolicy: {}` (server/seed.mjs:128-129, orchestrator.mjs:44-45), so with cap.requiresApproval=false every native resolves ALLOWED/capability.default; but a household that denies a famili.* id on agt_household would newly produce toolCalls status "blocked" and an `assistant.tool_blocked` audit row for a native — behaviour no test currently pins.
EVIDENCE: server/index.mjs:5045-5047; server/orchestrator.mjs:21-27; server/sms.mjs:341-342; server/group-agent.mjs:121-128; server/helpers.mjs:389-393; server/engine.mjs:391-392; server/test/assistant-agent.test.mjs:159-160

### F2 [medium]
Shape (a) (ladder wrap, requiresApproval unchanged) changes no existing assertion: natives already emit an `assistant.tool` audit row, no test asserts any `assistant.tool*` row, and the ladder's own tests pin that an ungated local Read/Write is untouched by every stance, by the kill switch, and by rule 4b.
IMPLICATION: (a) cannot literally route through executeToolForChat — resolveTool returns null for a non-registry id and the call would fail `unknown_tool` — so it means a new wrapper applying isToolStepAllowed + resolveEffectivePolicy + withTimeout + audit.
