# Rung 4 audit — can defineAction hold plan_meal (2026-09-23)

SUMMARY: homeops.plan_meal CAN be declared with defineAction as it stands: http is optional for an agent:true action (only agent:false forces a door), createListItem is the existing tool-only precedent, and a node probe confirms defineAction accepts agent:true with no http. Its input fits the fence — the ingredients string|object union is expressible as items with type:["string","object"] plus properties (validateInput branches on the actual type and emit-ts renders Array<string | {item; have?}>), replace/visibility/nestId are plain — but validator-first changes two error codes the tests pin (bad_slot, and bad_servings unless servings keeps createMeal's wide ["number","string","null"] wire). Its output mostly fits, with one hard limit: a nullable $ref is refused at load ("a $ref schema carries only a description") and validateInput follows $ref ignoring type, so `event: EventRecord|null` must be declared optional-not-nullable (omit the key) or as an inline nullable object; multi-$defs (MealRecord+EventRecord) merge fine. `delivers` is the only reach flag defineAction knows (there is no `external` field; engine derives external from kind provider/connector, always false for internal), and declaring plan_meal delivers:true would kill-switch-block and high-stakes the whole meal; the right shape is delivers:false with the Google step gated inside run like update_event/delete_meal — and that gate is MISSING today: plan_meal pushes to Google on calendarAutoSync alone with no externalActionsEnabled check. Structurally, option A (one agent-only action, existing body, declared flat output plus record fields) is the minimal "declared composite" and is legal now; option B (compose declared primitives via .run) cannot reproduce the event (createEvent has no mealId input, writes draft/provenance.via agent, and no declared patch/update primitives exist for dupe/replace/existing-event branches; .run composition also bypasses invoke validation); option C (schema-only, stay in INTERNAL_FUNCTIONS) has no mechanism — inputSchemaForCatalogTool only consults the registry, and defineAction requires run. Declaring requires deleting three hand rows (context.mjs INTERNAL_INPUTS, internal-functions.mjs entry, assistant-agent EXTRA_INPUT_KEYS), two of which would be silently shadowed rather than caught by tool-registry-consistency. The output shape is consumed FLAT by the iOS humanDetail formatter, summarizeForCard, engine eventId threading and four tests, so the declared output should keep the flat keys and add meal/event. The drift test only requires regenerating both copies; the putMeal( guard is already satisfied (plan_meal uses putMeal(newMealRecord(); patchMeal has no guard. Separately, the ADR, meals.mjs header and action-meals test header all claim plan_meal writes groceries through syncMealGroceries; it does not — it has its own loop with different source/visibility/normalisation.

## FINDINGS

### F1 [high]
plan_meal's Google push runs on calendarAutoSync alone with no household kill-switch check, and neither the engine's execResolved gate nor the policy ladder can catch it because the capability is a Write with delivers:false; declaring the composite delivers:true would over-correct by blocking and high-staking the whole meal, so a declared plan_meal must stay delivers:false and gate the Google step inside run as update_event and delete_meal do.
IMPLICATION: Whichever structural option rung 4 picks, the Google step needs an in-run `externalActionsEnabled !== false` guard (the replace path already has one for deleteGoogleCopy). defineAction has no `external` field and `delivers` means 'reaches a person' (policy.mjs:44-46); setting delivers:true would make the kill switch refuse the local meal+groceries+event too (policy rule 1) and make Balanced/autoAllow unable to clear it (policy 160-162, 245). Same reasoning applies to extractRecipe/estimateIngredients (web.mjs:533-551 calls api.openai.com; 569-570 reads a third-party page): outbound reads, not deliveries, and today classified by nothing.

### F2 [high]
A nullable $ref (`type:['object','null']` with `$ref`) is refused at load and would fail validation at runtime; `event: EventRecord | null` must be declared as an optional (omitted-when-absent) $ref, or as an inline nullable object that duplicates EVENT_RECORD; `google` and multi-$defs (MealRecord + EventRecord + TaskRecord in one action) are expressible.
IMPLICATION: Read-only node probe (importing validateInput/assertSchema/defineAction/renderActionsTs): `{type:['object','null'],$ref:'#/$defs/M'}` → assertSchema throws 'a $ref schema carries only a description'; bypassing it, validateInput(null) → 'input must be object, got null'. `{type:['object','null'],properties:{...}}` inline → assertSchema OK, null validates OK, renders `{ id: string; } | null`. `google: {type:'object', properties:{pushed:boolean, googleEventId:string, action:enum[created,updated], error:string}, required:['pushed'], additionalProperties:false}` renders `googleEventId?: string; action?: "created" | "updated"; error?: string`. So the composite should declare `event: { $ref: '#/$defs/EventRecord' }` NOT in `required` and return `...(event ? { event } : {})`; passing the same EVENT_RECORD/MEAL_RECORD/TASK_RECORD objects other actions use satisfies the emit-ts equality check. Output mismatch only warns once per field, never refuses.

### F3 [high]
plan_meal's result is consumed FLAT (title, groceryItems, eventId, mealId, google.pushed, note, slot) by the iOS run formatter, the chat card summariser, the engine's eventId threading and four server tests; a declared output that replaces those keys with {meal, event, groceriesAdded} silently degrades the mobile card and breaks the tests, so the declared output should keep the flat keys and add the records.
IMPLICATION: With `additionalProperties:false` every returned key must be declared or the once-per-field warning fires (define-action.mjs:105-107 → 188-191). ### F6 [medium]

### F7 [medium]
Option B (compose declared primitives via .run) cannot reproduce plan_meal's event or its dedup/replace branches: createEvent has no mealId input, writes status 'draft', source 'FamiliOS Assistant' and provenance.via 'agent' for an agent caller, and no declared updateMeal/replaceMeal/patch-event primitive exists; the createListItem precedent composes via .run, which bypasses invoke, so inner calls gain no validation anyway.
IMPLICATION: Routing the calendar step through createEvent.run would drop mealId (the key every cleanup path uses: replace at 360, delete_meal at assistant-agent.mjs:527, the idempotent `existing` lookup at 431), produce a draft instead of a confirmed meal event, and stamp provenance.via 'agent' not 'meal' — breaking internal-tools:82, scheduling-consistency:83-84/97-98 and the calendar's 'one dinner not two' guarantee. The dedup (patchMeal on dupe), replace (archive + unlink) and existing-event patch branches have no declared primitive to call. ## OPEN QUESTIONS
- Do the configured AI providers (OpenAI strict tool schemas, Anthropic, LM Studio/Ollama) accept `type: ["string","object"]` inside `items` in a tool inputSchema? createEvent already ships `startAt: {type:['string','null']}` to the model (action-tool-schema.test.mjs:34), which is evidence that type-arrays reach providers today, but a string|object union inside an array was not verified against any provider.
- Should the declared plan_meal resolve `nestId` via resolveVisibility (as createMeal does at meals.mjs:107-108) — today plan_meal passes `input.visibility` straight through and never reads nestId, so a nest meal from chat is currently impossible; declaring `nestId` changes behaviour, not just contract.
- Does `estimateIngredients` (direct api.openai.com call with the household's key, web.mjs:533-551) and `extractRecipe` (third-party page fetch/render) need a policy classification of their own for a Low-risk local Write? reachesOutside only sees delivers/external/Send-Download-Pay; neither the kill switch nor the group-chat deny list would stop these reads if plan_meal were reachable from a group thread (it is denied there today by id).
- Should `bad_slot` remain in errorCodes as documentation of the run-side check once the enum makes it unreachable through invoke, or be dropped and tool-input-validation.test.mjs:101-103 rewritten to expect invalid_input/field:'slot' (the create_task precedent)?
- Is the difference between plan_meal's grocery loop and syncMealGroceries (source 'assistant' vs 'meal', visibility unset vs copied, normaliser) intentional? If plan_meal is routed through syncMealGroceries, syncMealGroceries must return ids (it returns a count) or the composite's `groceryItems` count keeps coming from a separate loop.
- Would a declared plan_meal be placed in server/actions/meals.mjs (beside createMeal, sharing normalizeIngredients/TIME_RE) or its own file? Either is cycle-safe per the import grep, but the tasks.mjs header comment (line 9-10) and meals.mjs header (line 10-11) both need rewording.
