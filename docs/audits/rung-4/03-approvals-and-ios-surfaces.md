# Rung 4 audit — approvals pipeline and the iOS surfaces (2026-09-23)

SUMMARY: The approvals pipeline is generic end to end: an approval record is {id, connectorId, toolId, status, risk, category, preview, createdAt, expiresAt, decidedBy, decidedAt, requestedBy, source, allowedApproverRoles, consumedBy} with no input (pinned by approvals.test.mjs), and the real input lives on the parked run step that GET /api/runs exposes. On iOS, Inbox renders the raw toolId as the card title plus a generic "Label: value" dump of the run step input; the ApprovalSheet (mounted from Today, not Inbox) shows humanizeTool(toolId), the preview line and a boilerplate "why" sentence, and never shows the step input, so an approver of a queued famili.update_helper would see "Update helper / Change a helper" and no instructions. The Ask thread expects AssistantToolCall.status in {done, failed, blocked, awaiting_approval}; awaiting_approval renders an amber "Waiting for approval · <label>" chip linking to /inbox, while failed and policy-blocked render identically as a coral label with no reason, and the live server-run card compares against "waiting_approval" although the engine only ever writes "waiting_for_approval", so a parked run's badge reads "Doing it". ctx.helperChanged has zero consumers on either client (api.ts AssistantResult omits it); the Helpers list refetches on focus, but the helper editor loads once on mount by design, so a chat edit to an open helper is not reflected until pull-to-refresh. The hardest blocker for routing native writes through queueApprovalRun today is that the run engine's resolveToolBase knows only internal/provider/connector tools, so a famili.* step fails the run with "Unknown tool: famili.update_helper" before any approval is created. summarizeForCard produces readable summaries for update_event, delete_event, delete_task and delete_meal only; update_task, delete_memory, create_helper, update_helper and run_helper fall through to a 120-char JSON dump, which the helper editor's ToolReceipts badge displays verbatim. All parked/expired wording ("nothing has been sent yet", "That approval expired — nothing was sent", push body "<toolId> — <preview>") assumes an outbound send and would read wrongly for a local helper edit, and the 30-minute approval TTL would silently expire it. Finally, the prompt (lines 811-812) and the create_helper description (line 593) promise "It is created immediately" / "it applies immediately", while line 803 tells the model an awaiting_approval result "did NOT happen yet"; gating create_helper/update_helper contradicts the prompt as written, and helperChanged would no longer be set in the chat ctx because the write would execute inside the run.

## FINDINGS

### F1 [high]
The durable-run engine cannot execute a famili.* step: resolveToolBase resolves only internal, provider and connector tools, startRun records requiresApproval:false for an unresolved tool, and _drive fails the run with unknown_tool before any approval is created — so reusing queueApprovalRun for native writes yields a failed run, not a parked approval.
IMPLICATION: Rung 4 cannot simply route the second buildToolSet loop through executeToolForChat/queueApprovalRun: the native tools must first be registered somewhere resolveToolBase can find them (declared actions via define-action, or a fourth resolver branch) and execResolved must be able to run them with a session-shaped ctx, or every gated native call ends as a red 'failed' receipt in Ask with message 'Unknown tool: famili.update_helper'.
EVIDENCE: server/engine.mjs:263-274; server/engine.mjs:513-521; server/engine.mjs:722-726; server/assistant-agent.mjs:783-785; server/assistant-agent.mjs:727-745

### F2 [high]
The iOS approval surfaces are generic over toolId with no per-tool special-casing: Inbox titles the card with the raw toolId and appends a generic Label: value dump of the run step's input; ApprovalSheet shows humanizeTool(toolId) (last dot segment), the first preview line, a boilerplate risk sentence and the preview well, but never the step input; a queued famili.update_helper would therefore show an approver 'famili.update_helper / Change a helper' (Inbox) or 'Update helper' (sheet) with the new instructions visible only in Inbox, truncated to 117 chars.
IMPLICATION: Nothing on iOS breaks for an unknown toolId, but a gated helper edit is approvable from Today/ApprovalSheet without the approver ever seeing the replacement instructions, and Inbox shows a raw dotted id as the headline. Rung 4 should make `preview` carry the human summary (queueApprovalRun passes title = d.name, e.g. 'Change a helper') and consider a multi-line preview, since the sheet is the only surface that renders preview beyond its first line.

### F3 [medium]
In the Ask thread a tool call renders from AssistantToolCall.status ∈ {done, failed, blocked, awaiting_approval}: awaiting_approval is an amber clock chip 'Waiting for approval · <label>' that navigates to /inbox; failed, blocked and ok===false all render as the same coral triangle + label with no reason text, so a policy-blocked native write is indistinguishable from a crashed one; and the live server-run card's badge tests status === "waiting_approval" while the engine writes "waiting_for_approval", so a parked run is badged 'Doing it'.
IMPLICATION: A gated native write would show correctly as 'Waiting for approval · Change a helper' in the receipt row, but the live run card directly beneath it would say 'Doing it' for the same run; and a ladder BLOCKED verdict (e.g. kill switch, agent deny list) would show as a bare coral label with the reason only in the model's prose. Fix the string compare and surface c.summary on failed/blocked before making native writes ladder-gated.

### F4 [medium]
ctx.helperChanged is returned by runAssistantAgent but consumed by nothing on either client: apps/mobile/src/lib/api.ts AssistantResult has no such field and grep finds no reader in apps/mobile or src/. The Helpers list refetches on focus, but the helper editor deliberately loads once on mount and only refreshes on pull or after 'Run now', so a chat edit to a helper whose editor is open is not reflected.
IMPLICATION: Today a chat-created/edited helper already appears in Helpers on next focus without helperChanged; if the write moves into an approval-resumed run, helperChanged would be set inside the engine (not the chat ctx) and the response field would be false anyway — so nothing is lost on iOS, but the field is dead weight and the editor-open-while-chat-edits staleness (and dirty-compare against a stale copy) exists regardless of approvals.

### F5 [medium]
summarizeForCard yields a readable one-liner for only four of the nine native writes (update_event via r.event.title; delete_event, delete_task, delete_meal via r.title); update_task ({task}), delete_memory ({deleted,text}), create_helper (no r.note except the Adult-Member personal case), update_helper ({updated,...}) and run_helper ({ran,said,did}) fall through to short(r, 120) — a 120-char JSON dump — which the helper editor's ToolReceipts renders as the badge label and the model's history fold and no-answer fallback quote.
IMPLICATION: Nothing crashes: Ask's ToolCallsRow ignores summary, buildResultLinks silently skips famili.* steps (no 'View helper' link) and runOutcomeText falls to 'Done — "Change a helper" finished (1/1 steps).' because toolDelivers() returns false for an id in no catalog. But a helper's own receipts and the model's memory of the turn already carry JSON like {"updated":true,"helperId":"agt_…" — worth giving these five results a title/note before they start flowing through the run pipeline too.

### F6 [medium]
Every parked/expired message assumes an outbound send: the run-parked conversation status says 'nothing has been sent yet', the expired outcome says 'nothing was sent', the Ask step row says 'Expired — nothing was sent', and the push body is '<toolId> — <preview>'; the approval TTL is 30 minutes, after which the run is swept to expired.
IMPLICATION: A gated delete_task or update_helper would push 'Approval needed: famili.update_helper — Change a helper' and, if unanswered for 30 minutes, tell the family 'nothing was sent' about a local edit. The wording is keyed on the assumption that gated steps deliver; rung 4 needs either action-aware copy ('nothing has changed') or a longer TTL for local writes.
EVIDENCE: server/assistant-runs.mjs:456-461; server/assistant-runs.mjs:324-326; apps/mobile/src/app/(ask)/index.tsx:1212-1214; server/notify.mjs:109-110; server/store.mjs:742; server/engine.mjs:1170-1171

### F7 [medium]
The prompt and the create_helper tool description promise immediacy — 'It is created immediately' (line 811 and line 593) and 'it applies immediately, so say exactly what changed' (line 812) — while line 803 tells the model an awaiting_approval result 'did NOT happen yet'; gating create_helper/update_helper (or run_helper, whose description says 'Returns what it did') would make the prompt self-contradictory, and ctx.helperChanged = true is set inside d.run so it would no longer be set on a deferred write.
IMPLICATION: If rung 4 puts helper writes behind the ladder, lines 593, 611-612 (prompt 811-812) and 650 must be rewritten to the 'may be queued for approval' shape the catalog tools use (line 690's approvalNote), or the model will narrate 'I created X, it next runs at 7:00' over an awaiting_approval result. The safer split is: keep create/update/run_helper immediate (they are already role-gated to Adult Member+, not group, not asHelper) and gate only the destructive event/task/meal/memory writes.
EVIDENCE: server/assistant-agent.mjs:811-812; server/assistant-agent.mjs:593; server/assistant-agent.mjs:803; server/assistant-agent.mjs:650; server/assistant-agent.mjs:643-646

### F8 [low]
Native tool definitions carry no risk (add() records only action), and createApproval defaults a missing risk to High, whose default approver roles are Owner and Adult Admin only; an Adult Member who asks chat to edit their own personal helper would see the approval in Inbox (as requester) but could not approve it, and ApprovalSheet maps the server's 'approver_not_allowed' 403 to the generic 'Something went wrong' alert.
IMPLICATION: Whatever rung 4 chooses, each native write needs an explicit risk (and delivers:false) at definition time, or the ladder will treat 'mark task done' as High and route every Adult Member's self-edit to the Owner; and the sheet's error mapping should recognise approver_not_allowed so the blocked approver gets the intended sentence.
