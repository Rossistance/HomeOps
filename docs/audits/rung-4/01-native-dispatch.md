# Rung 4 audit — native famili.* dispatch (2026-09-23)

SUMMARY: The 16 native famili.* tools (6 reads, 6 writes, 4 helper-management tools) are registered by the second loop in buildToolSet (server/assistant-agent.mjs:727-745) and execute as `await d.run(input)` followed by one `assistant.tool` audit row; nothing in that path calls resolveTool, isToolStepAllowed, resolveEffectivePolicy, getRiskOverride, requiresApproval/queueApprovalRun or withTimeout, and the `add()` registrar records no `risk` or `requiresApproval` metadata for a ladder to consult. Catalog tools in the first loop (683-725) call executeToolForChat (server/engine.mjs:384-434), which runs the whole ladder inside `if (agent)` and then a 60s withTimeout around execResolved. On the critical question: `agent` is non-null on every production caller today — POST /api/assistant and /api/assistant/stream pass `ensureDefaultHelper()` (agt_household, never null in-tenant), group-agent passes `resolveActingHelper({session})`, sms passes `resolveActingHelper({session})`, and runHelper passes the helper record itself — so the `if (agent)` block runs for every catalog call on every surface, and the honest statement is "the ladder runs for all catalog tools; native tools are the only tool-execution path outside it", not "the ladder only runs for helper turns". Note that for app/SMS/group turns the acting agent is agt_household with empty allow/deny lists and `approvalPolicy: {}`, so ladder rules 2-4 and 6-6b are vacuous there; what actually bites for those surfaces is rule 1 (kill switch), rule 4b (group only), rule 5 (risk override) and rule 7 (autonomy stance). Native writes substitute hand-rolled guards: `canWrite = roleAtLeast(session.role, "Limited Member")`, ownership via `isAdultRole`/createdBy/ownerId/assignedMemberId, `seeable` channel filtering on reads, and three inline copies of the kill switch before Google calls. Consequences: rule 4b protects nothing native (a Limited Member in the group thread gets catalog writes parked for an adult but native famili.update_task/update_event/delete_* execute immediately), helper allow/deny lists cannot see famili.* ids (no fixture, seed or CHAT_DENIED_TOOL_IDS names one, and the native loop never consults permittedIds), the group channel still exposes create/update/run_helper to adults because nativeTools gates on `!ctx.asHelper` while only the prompt gates on `channel !== "group"`, and native audit rows lack connectorId/durationMs/agentId and never emit `assistant.tool_blocked`. ADR-003's follow-up ladder item 4 already names this as "the next real architectural decision".

## FINDINGS

### F1 [high]
The native execute path (assistant-agent.mjs:734-743) runs `d.run(input)` directly and skips every ladder step the catalog path performs in executeToolForChat: resolveTool (engine.mjs:388), isToolStepAllowed (392), resolveEffectivePolicy with kill switch/denied/allowed/alwaysApprove/4b/override/autoAllow/unattended/stance (398-419), the requiresApproval→queueApprovalRun branch (420; assistant-agent.mjs:709-719), getRiskOverride (410), and withTimeout(RUN_STEP_TIMEOUT_MS=60_000) (426). The native registrar records no `risk` or `requiresApproval` field at all, so there is nothing for a ladder to consult even if it were wired.
IMPLICATION: Rung 4 must decide whether famili.* become declared actions executed through executeToolForChat (gaining risk/requiresApproval metadata, the ladder, the timeout and uniform audit) or remain a documented second class of tool with an explicit, tested contract for what they may and may not do.
EVIDENCE: server/assistant-agent.mjs:734-743; server/assistant-agent.mjs:274; server/engine.mjs:388-420; server/engine.mjs:426; server/engine.mjs:30

### F2 [high]
`agent` is non-null on every production caller of runAssistantAgent, so the `if (agent)` ladder in executeToolForChat runs for every catalog tool call on every surface today; the honest statement is 'the ladder applies to all catalog tools and native tools are the only execution path outside it', not 'the ladder only runs for helper-driven turns'. Callers: POST /api/assistant and /api/assistant/stream pass ensureDefaultHelper() (agt_household); group-agent runWakeTurn and sms respondInTenant pass resolveActingHelper({session}) (agt_household in-tenant); runHelper passes the helper record. ensureDefaultHelper always returns an agent (returns existing or putAgent then getAgent). Caveat: agt_household ships with empty allow/deny lists and `approvalPolicy: {}`, so rules 2-4 and 6-6b are no-ops for app/SMS/group turns; only rule 1 (kill switch), 4b (group only), 5 (override) and 7 (stance) can change an outcome there.
IMPLICATION: Rung 4 should frame the gap as 'native tools are outside a ladder that otherwise covers every surface', and can rely on the `if (agent)` block being live everywhere; the `agent = null` default is dead in production and could be made a hard error rather than a silent ladder-skip.
EVIDENCE: server/index.mjs:5044-5047; server/index.mjs:5116-5128; server/group-agent.mjs:121-129; server/sms.mjs:331-342; server/helpers.mjs:389-393; server/orchestrator.mjs:27-64; server/orchestrator.mjs:70-78; server/assistant-agent.mjs:885

### F3 [high]
Policy rule 4b (actorIsAdult) protects nothing native. The catalog path passes `actorIsAdult: ctx.channel === "group" ? isAdultRole(session.role) : null` so a Limited Member's approval-gated catalog write in the group thread is parked for an adult; native writes gate only on `canWrite = roleAtLeast(session.role, "Limited Member")` plus ownership (createdBy / ownerId / assignedMemberId-for-status / isAdultRole), so the same Limited Member can complete, re-date, reassign or delete their own tasks, move their own events and delete their own meals and memories immediately, in the group thread, with no approval record.
IMPLICATION: The group-channel hardening (rule 4b, group-injection tests) is only half-applied: whatever rung 4 decides for native tools must state whether native writes by non-adults in the group lane should be parked like catalog writes, or whether ownership checks are deemed sufficient — and test it.
EVIDENCE: server/assistant-agent.mjs:701-704; server/policy.mjs:144-146; server/assistant-agent.mjs:271-272; server/assistant-agent.mjs:469-471; server/assistant-agent.mjs:394-396; server/auth.mjs:23-27

### F4 [medium]
Helper allow/deny lists cannot reach native tools. buildToolSet computes `permittedIds` from pruneCatalogForPrompt(catalog, {agent}) and applies it only to the catalog loop; the native loop `for (const d of nativeTools(ctx))` is unconditional, and isToolStepAllowed/resolveEffectivePolicy never see a famili.* id. No seed, fixture or constant names a famili.* id in allowedToolIds/deniedToolIds (seed.mjs:128 is empty, CHAT_DENIED_TOOL_IDS lists only homeops/web/gmail/etc., migrated agents.json contains no 'famili'). So a helper with a six-tool allow-list still receives all 12 native read/write tools (helper tools drop only via asHelper). Separately, pruneCatalogForPrompt keeps every internal/homeops.* tool in the prompt regardless of the agent's lists (`isAlwaysAvailableTool(t) || agentPermitsTool(...)`), relying on isToolStepAllowed at execution to block a denied one.
IMPLICATION: The Helpers permission UI and the allow/deny concept are silently incomplete: a family cannot deny a helper famili.delete_event. Rung 4 must either give native tools ids the lists can address (by making them actions) or document that helper permissions govern only the catalog.
EVIDENCE: server/assistant-agent.mjs:671-672; server/assistant-agent.mjs:683-684; server/assistant-agent.mjs:727-731; server/context.mjs:242-245; server/context.mjs:205-216; server/helper-shape.mjs:95-105; server/seed.mjs:128; server/group-chat.mjs:97-110

### F5 [medium]
The group channel still hands adults the helper-management tools. nativeTools gates famili.list_helpers/create_helper/update_helper/run_helper on `roleAtLeast(session.role, "Adult Member") && !ctx.asHelper` with no channel check, while instructionsFor receives `managesHelpers: ... && channel !== "group"` and the comment calls it 'the one named exception to "the group gets the complete tool menu"'. Only the prompt line is suppressed; an Adult Member/Admin/Owner texting in the bound iMessage group can still invoke famili__create_helper, famili__update_helper (including autonomy 'act') and famili__run_helper. No test asserts the group toolset excludes them (helpers.test.mjs:280 covers asHelper only; group-agent-turn.test.mjs:129 asserts only that famili__list_events is present).
IMPLICATION: A stated security boundary (standing autonomous actors are not created from a group text) is enforced in prose only; because native tools have no ladder, there is no second layer to catch it. Rung 4 should close this with a channel gate in nativeTools plus a test, whichever direction the native-tools decision goes.
EVIDENCE: server/assistant-agent.mjs:567-569; server/assistant-agent.mjs:923-930; server/assistant-agent.mjs:911-913; server/test/helpers.test.mjs:278-280; server/test/group-agent-turn.test.mjs:128-130

### F6 [medium]
Audit rows diverge between the two paths. The catalog path writes `assistant.tool` with connectorId and durationMs and, on refusal, `assistant.tool_blocked` with agentId and reason/rule; the native path writes `assistant.tool` with neither connectorId, durationMs nor agentId, never writes `assistant.tool_blocked`, and reports a native refusal (read_only_profile, forbidden, not_event_owner, read_only_layer, external_actions_disabled, household_helper) as `assistant.tool ok:false error:<code>`. ctx.toolCalls for a native call is only ever `done` or `failed`, never `blocked`/`awaiting_approval`.
IMPLICATION: Any audit query, dashboard or test that keys on tool_blocked, durationMs or agentId undercounts native activity; a helper-run summary counting `blocked` never sees a native refusal. Rung 4's audit contract should be one shape for both paths.
EVIDENCE: server/engine.mjs:430; server/engine.mjs:394; server/assistant-agent.mjs:739-742; server/assistant-agent.mjs:721

### F7 [medium]
famili.run_helper starts a full nested agent turn as the CALLER's session (runHelper uses `session ?? sessionForHelper(helper)`, and the tool passes `session`), with `agent: helper, asHelper: true`. The inner turn's catalog tools go through the ladder attributed to the helper, but the inner turn again has all 12 native read/write tools with no ladder, now scoped by the caller's role and the helper's visibility. run_helper itself is declared action 'Write' yet performs no kill-switch, approval or budget check beyond what the inner runAssistantAgent applies (aiBudgetExhausted at its top).
IMPLICATION: A native tool is the one place a chat turn can spawn a second autonomous turn with a different identity; rung 4 should decide whether run_helper is a declared action (auditable, ladder-visible) and whether a chat-triggered helper run should act as the caller or as sessionForHelper.
EVIDENCE: server/assistant-agent.mjs:652-658; server/helpers.mjs:370-371; server/helpers.mjs:347-355; server/assistant-agent.mjs:889-891

### F8 [low]
The household kill switch is re-implemented by hand inside three native writes (update_event, delete_event, delete_meal), each checking `getSettings(hh).externalActionsEnabled` only before a Google call, rather than via the ladder's rule 1 / execResolved's `reachesOutside` check; and because native tools carry no risk class, a household risk override recorded for a famili.* id (getRiskOverride is keyed only by householdId+toolId) can never take effect on the native path.
IMPLICATION: Three copies of rule 1 with three wordings is exactly the drift ADR-003 exists to remove; if native tools become actions with `delivers`/risk metadata, rule 1 and rule 5 apply for free.
EVIDENCE: server/assistant-agent.mjs:413; server/assistant-agent.mjs:441-443; server/assistant-agent.mjs:524-529; server/policy.mjs:104-108; server/store.mjs:1366-1370

## OPEN QUESTIONS
- Does the AI SDK's `timeout: { stepMs: STEP_TIMEOUT_MS }` (assistant-agent.mjs:940) bound tool `execute` duration, or only the model call? If not, a native `d.run` (e.g. a hung Google call in update_event) has no per-tool timeout at all, unlike the catalog path's 60s withTimeout.
- SMS edge: respondInTenant sets `householdId = member.householdId ?? "local"` (sms.mjs:323) while the tenant is `matches[0].householdId`; if a member row ever lacks householdId in a non-'local' tenant, resolveActingHelper (orchestrator.mjs:76) returns `getAgent("agt_household")` for the resident tenant, which could be null and would silently skip the ladder. Could not confirm from code whether member rows always carry householdId.
- isToolStepAllowed is declared `(agent, toolId)` (helper-shape.mjs:95) but engine.mjs:392 and :750 pass a third `{ householdId, actorId }` argument that is ignored. Is nest-scoped allow/deny intended there (getRiskOverride is nest-aware) or is the extra argument vestigial?
- policy.mjs:113/117 use `agent?.deniedToolIds ?? agent?.deniedFunctionIds` (first-defined wins) whereas isToolStepAllowed and agentPermitsTool concatenate both lists. With seeded `deniedToolIds: []` the *FunctionIds lists are never read by resolveEffectivePolicy; harmless today because isToolStepAllowed runs first, but is the divergence intentional?
- Can PUT /api/risk-overrides accept a famili.* toolId (index.mjs:4227)? If it validates against toolCatalog the override is impossible; if not, a family could record an override that the native path never honours.
- famili.list_members returns the full roster regardless of channel (assistant-agent.mjs:320-321); is roster exposure in the group thread intended to be governed by the prompt rule alone ('volunteer nothing else about the family — no roster')?
