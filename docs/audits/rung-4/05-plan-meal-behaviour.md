# Rung 4 audit — plan_meal behaviour vs the rung 3 meal actions (2026-09-23)

SUMMARY: homeops.plan_meal (D:/FamiliOS/FamiliOS/server/internal-functions.mjs L287-448) is a hand-written INTERNAL_FUNCTIONS entry, not a defineAction: it validates title/slot/servings by hand, normalises ingredients to {item,have} (cap 60), self-enriches an ingredient-less meal through web.mjs (extractRecipe = outbound HTTP fetch + optional headless render + same-site crawl + OpenAI gpt-4o-mini text extraction; estimateIngredients = OpenAI gpt-4o-mini), de-dupes by normalised title within 8 days (and against ANY date when no date is given), handles slot occupancy (replace:true archives + deletes events/Google copies + unlinks open groceries; else shifts up to 7 days; else double-books with a note), writes the meal via newMealRecord(source "assistant"), writes groceries by hand via putTask(newTaskRecord) rather than through syncMealGroceries despite meals.mjs, action-meals.test.mjs and ADR-003 all stating it does, upserts one calendar event by mealId, pushes to Google when calendarAutoSync===true, and returns the flat {id, mealId, title, date, slot, groceryItems, eventId, google, note?}. Consumers of that flat shape are: engine deterministicFill's eventId threading (reads result.eventId ?? result.id ?? result.event?.id, ev_ prefix), engine summarize() which stringifies the result into step.detail (200 chars) and the idempotency summary, assistant-agent summarizeForCard (r.title), and on the client only apps/mobile/src/lib/format.ts humanDetail (title/groceryItems/eventId) fed by step.detail; buildResultLinks and runResultGroups never match plan_meal; nothing in src/ reads it. The schema the model sees is the KEY_HINTS join over the INTERNAL_INPUTS row (EXTRA_INPUT_KEYS row is now fully redundant), declares ingredients as string[] although the handler accepts objects, omits visibility which the handler reads unnormalised, and is not enforced on any path (AI SDK jsonSchema without validate; engine passes step.input straight to run). IDEMPOTENT_TOOLS lets a plan_meal step that was mid-flight at a restart be re-driven; group-chat's CHAT_DENIED_TOOL_IDS denies plan_meal to the agt_chat voice identity and that list is persisted onto the helper record by id, so a rename would silently escape it. index.mjs PATCH /api/meals/:id, DELETE, /to-calendar plus famili.delete_meal hold a third and fourth copy of the slot-time/title/notes composition, the grocery-unlink expression and the Google-copy deletion loop, with small divergences (event visibility, done-only unlink, autopush gating). Nine assertions across four test files read the flat result keys, and three tests send object ingredients / expect bad_slot and bad_servings error codes that a strict typed validation would turn into invalid_input.

## FINDINGS

### F1 [medium]
Every consumer of plan_meal's flat result is enumerable and small: on the server only engine deterministicFill (eventId threading), engine summarize()->step.detail/idempotency summary, and assistant-agent summarizeForCard read keys; buildResultLinks and runResultGroups never match plan_meal; on the client only apps/mobile humanDetail reads title/groceryItems/eventId, and it receives the result only as the 200-char JSON in step.detail, which truncates (and therefore fails JSON.parse) whenever a note is present or ids/title exceed ~15 chars; src/ reads nothing.
IMPLICATION: A composite that returns {meal, event, groceriesAdded, google, note} keeps eventId threading working (result.event?.id is already read), changes summarizeForCard from the meal title to the event title ('Dinner: X'), and only nominally changes the mobile line (it already falls back to 'Done — structured result saved' for most plan_meal results because summarize() cuts at 200 chars; with 16-hex ids a 15-char title with no note is exactly 200). No web client code needs to change.

### F2 [medium]
